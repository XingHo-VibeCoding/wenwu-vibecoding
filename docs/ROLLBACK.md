# 回滚手册 · wenwu-vibecoding

> 适用对象：前端（CloudBase 静态网站托管）+ 云函数（`cloudfunctions/scenes/`）+ 数据库（PostgreSQL）。
> 首次撰写：2026-10-11（Day 27）—— 同日**真实执行过一次完整回滚演练**，记录见 §八。

---

## 一、什么情况必须回滚（判断表）

先定性质，再动手。**能"补一步"解决的，不要回滚。**

| 现象 | 怎么确认 | 判定 | 动作 |
|---|---|---|---|
| 线上白屏 / 打不开 | 无痕打开；`python tests/check-live-version.py` 抓不到指纹 | **紧急，必须回滚** | 前端回滚（§四 路径 B） |
| 页面能开但内容明显是旧版 | `check-live-version.py --expect v1.0` → FAIL，指纹=旧版 | 上次发布没成功 / 传错目录 | **重传正确产物**即可，不算回滚 |
| 线上指纹不符合任何登记版本 | 校验器结果 `UNKNOWN` | 上传只完成了一半（如只传了 JS 没传 index.html） | 补齐上传 → 再校验 |
| `/api/health` 非 200、**所有**接口都挂 | 直连网关 `/api/health` | 云函数或环境问题 | 回退云函数（§五），**前端不用动** |
| 单个读接口 500，其余正常 | 逐接口比对 | 大概率**缺 GRANT**（读=`USAGE`+`SELECT ALL`） | **不要回滚**，补 GRANT（缺 GRANT 必 500，而读接口完全不受影响，极易误诊） |
| 页面显示"离线内容"降级 | 看是否降级 badge | 网络 / 接口不通 | 先排网络，再查网关；未必需要回滚 |
| **真密钥被推到公网** | 检查 5 FAIL 且命中是**真值** | 最高优先级安全事件 | ① 先 **rotate / 吊销密钥** ② 再回滚 + 清理暴露面 |
| 只是文案、样式小瑕疵 | 肉眼确认 | 不影响使用 | **不回滚**，下一版修 |

> 判断口诀：**先分清是"前端产物"问题、"云函数"问题、还是"数据库"问题**——三者的回滚动作完全不同，改错层等于二次事故。

## 二、回滚前准备

1. 记下**当前线上指纹**（回滚后再校验用）：`python tests/check-live-version.py`
2. 确认目标版本**存在且可构建**：`git log --oneline` 找到目标提交 → `git switch --detach <提交>` → 构建。
3. 工作树必须干净：`git status`（脏工作树会让 `git switch` 拒绝或带出意外改动）。
4. **告知影响面**：回滚期间线上是旧版（分钟级），确认可接受。

---

## 三、路径 A：平台一键回退 —— ❌ 本项目**不适用**（实测证据）

CloudBase 静态网站托管的本质是**一个对象存储桶**（桶名 `2cd6-static-wenwu-331122-…-1498877015`）：

- 控制台「文件管理」只有 **新建文件夹 / 上传文件夹 / 上传文件 / 删除** —— 全是文件操作，**没有**「历史版本 / 版本管理 / 回滚」入口（2026-10-11 实查）。
- 「网站部署」「基础配置」两个标签也没有版本回退功能。
- 上传 = **覆盖**，平台**不留部署快照**。

**结论**：**回滚 = 重新上传旧产物**（即路径 B）。这也是为什么「发布时留档产物 + 打 tag」是硬性要求。

> 加分发现：桶里的历史 `assets/*.js` **不会被自动清理**（实查仍留着 9-30、10-04、10-07 的旧 JS）。
> 也就是说——**只要手上还有对应的旧 `index.html`，这些残留文件就是现成的额外回滚点**。
> 但**不能依赖它**：上传流程随时可能被清理策略改变，正解仍是自己留档。

## 四、路径 B：重新上传旧产物（本项目唯一路径）

### 执行步（以回滚到 `4c264a4` 为例）

```powershell
# 1) 切到目标版本（游离头）
git switch --detach 4c264a4

# 2) 构建（本机唯一可靠姿势；中文路径下 npm 不可靠）
& "C:\Users\zuwen\.workbuddy\binaries\node\versions\22.22.2-3\node.exe" `
  "C:\Users\zuwen\Desktop\vibecoding实战工作区\web\node_modules\vite\bin\vite.js" `
  build "C:\Users\zuwen\Desktop\vibecoding实战工作区\web"

# 3) 记录旧产物指纹（后面校验用），然后上传
```

上传（人工，控制台）：
1. 静态网站托管 → 文件管理 → **进入 `wenwu-vibecoding/`**
2. 「上传文件」选 `web\dist\index.html`
3. 「上传文件夹」选 `web\dist\assets`
4. 层级确认：`wenwu-vibecoding/index.html` + `wenwu-vibecoding/assets/*`

### 恢复（回滚完再把目标版本装回来）

```powershell
git switch main                 # 或切到要恢复的 tag / 提交
git restore --worktree .        # ⚠️ 见坑 1
& "<node.exe>" "<repo>\web\node_modules\vite\bin\vite.js" build "<repo>\web"
# 核对字节数与留档一致后，重复上面的人工上传
```

### 三个实测坑

1. **`git switch` 可能不落地全部文件**：2026-10-11 演练中，`git switch main` 报出 13 个文件 `D`（工作区缺失，索引里有；两个提交都含这些文件）。**用 `git restore --worktree .` 全部补回**，然后**必须复核 `git status` 干净**再去构建 —— 否则会构建出残缺产物。
2. **上传层级**：`index.html` 必须在 `wenwu-vibecoding/` **根**，别多套一层（`wenwu-vibecoding/wenwu-vibecoding/…` 会导致 404）。若「上传文件夹」多套了一层，改用"新建文件夹 `assets` → 进去 → 上传文件"。
3. **CDN 缓存**：验证时用**带随机 query 的 URL**（`…/index.html?t=<时间戳>`）绕缓存；浏览器侧用无痕或 `Ctrl+Shift+R`。

## 五、云函数回滚

- 代码位置 `cloudfunctions/scenes/`：`index.js`（接口层）+ `repository.js`（数据层）。
- **必须两文件一起部署**（`index.js` 里 `require("./repository")`）——只传一个必然运行时报错。
- 回退动作：`git switch --detach <旧提交>` → 取 `cloudfunctions/scenes/` 两个文件 → 重新部署。
- 四条铁律（踩过）：① `package.json` 永不替换 ② 纯 ASCII、零 `//` ③ 函数收到路径 = 浏览器路径 − 路由前缀 ④ 永不回吐 `req.headers`。
- ⚠️ **"部署成功 ≠ 能跑"**：部署完必须打一次 `/api/health` + 一个读接口验证。

---

## 六、数据库：❌ **绝不回滚**

- `db/schema.sql` **含 `DROP`**，库里已有真实数据 → **整份执行 = 清库**（永远不要再跑 schema.sql）。
- `db/seed.sql` 同理，重跑会覆盖/重复插入。
- 若数据被写坏：**按行修**（`PATCH` 单个 step / 用 `db/seed.sql` 里的原始值定向订正），**不要整表重建**。
- ⚠️ 线上库探测必须**不落库 / 可回滚**（教训：探针曾把 `difficulty_level` 从 1 改成 3）。
